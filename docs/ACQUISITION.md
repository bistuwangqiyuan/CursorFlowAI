# 获客方案 —— 本项目的主要矛盾

> 本章篇幅刻意写得比产品方案更长。理由在下面第 1 节。
> 所有数字由 `model/acquisition.py` 生成，`python model/acquisition.py` 可复算。

---

## 1. 为什么获客是主要矛盾，而不是产品

`model/funnel.py` 的稳态方程给出一个无法回避的结论：

```
每 1,000 个精准访客 → 45 注册 → 1.35 付费客户 → $25.65 新增 MRR
7% 月流失下，稳态客户数 = 月新增 ÷ 月流失率
维持 $1,000 MRR（52.6 个客户）需要每月持续 2,729 个精准开发者访客
```

**关键在"持续"二字。** $1,000 MRR 不是一个一次性达成的里程碑，而是一台每月必须喂进 2,729 个访客才能维持不掉的机器。停止喂料，14.3 个月后归零。

与此同时，产品侧的约束却相对宽松：C12 是纯 YAML/AST 规则分析，`model/opportunity_scoring.py` 给它的"20 小时每周可交付性"打了 9 分，"边际成本结构"打了 10 分。**换句话说，产品能不能做出来基本不是问题；做出来之后有没有人看见，才是问题。**

用矛盾分析的语言说：产品是次要矛盾，获客是主要矛盾。集中力量解决主要矛盾，意味着 BP 的篇幅、阶段目标、止损线都要围绕流量来组织。

**一个必须先说清的反直觉事实：** 流量需求对"是否要求信用卡"这一个开关极度敏感。

| 口径 | 每千访客付费客户 | 维持 $1,000 MRR 所需月访客 |
|---|---|---|
| 不要信用卡 | 1.35 | **2,729** |
| **要信用卡** | **3.70** | **995** |

要卡片会让注册量掉约 22%，但签约转化率高 3.5 倍，净效果是**所需流量下降 63.5%**。
**这是一个零成本的产品决策，却比任何获客技巧都更能改变结局。** 依据：ChartMogul《The Conversion Report》，200 个 B2B 软件产品，https://chartmogul.com/reports/saas-conversion-report/

## 2. 不予采纳的渠道，以及为什么

先排除，再建设。以下渠道在本项目的约束下**结构上不成立**，不写进计划：

| 渠道 | 为什么不行 | 证据 |
|---|---|---|
| **付费广告** | 现金上限 $4,000，且开发者对广告免疫度高。买 2,729 个精准开发者访客的月成本会超过全部预算。 | 硬约束 |
| **冷邮件群发 / LinkedIn 私信轰炸** | 违反第〇条（向善）与第九条（直言有度）。骚扰不是获客。 | 工作原则 |
| **企业销售** | 与"零人工"硬冲突。该赛道 $50K 以上合同在 2026 年依然无法零人类参与成交（安全问卷、MSA 谈判、DPA、供应商风险评估）。 | research/sources.md §4.5 |
| **把一次 HN 头版当成渠道** | 10,000–30,000 UV/24h，但 **48 小时内衰减到零**。IndieLaunches 对 326 个 HN 项目的统计显示，HN 本身绝大多数是**次要**渠道（被提及 201 次），真正的主渠道是口碑（40 次）与 SEO（27 次）。 | research/BENCHMARKS.md §3 |
| **指望第一年靠 SEO** | Ahrefs 追踪 100 万个随机 URL：新页面 12 个月内进入 Google 前十的概率仅 **1.74%**；高搜索量词仅 **0.3%**。 | https://ahrefs.com/blog/how-long-does-it-take-to-rank-in-google-and-how-old-are-top-ranking-pages/ |
| **内容农场式批量 AI 文章** | 违反第〇条与第二十条（求实效）。而且本轮调研中被 AI 内容农场污染的正是这个领域，我不能一边隔离它们的数据一边成为它们。 | research/sources.md §0 |

**一条纪律：任何渠道若说不出"人为什么会来"的机制，就不写进计划。** 只写渠道名（"我们会做内容营销"）而不写机制，属于第二十条禁止的"漂亮的空话"。

## 3. 四条复利渠道 + 一条脉冲

复利与脉冲的区别是本章的组织原则：**复利渠道的存量越大流量越多，可计入稳态；脉冲一次性衰减到零，只能作为叠加事件，绝不计入稳态基线。**

### 3.1 渠道台账

| 渠道 | 复利 | 第 12 月 | 第 24 月 | 第 36 月 | 等级 |
|---|:---:|---:|---:|---:|---|
| 免费 GitHub Action 本体（产品即渠道） | 是 | 180 | 600 | 1,100 | D |
| 程序化 SEO 知识库（180 页） | 是 | 0 | 440 | 700 | A（排名概率）/ D（单页流量） |
| 负责任披露飞轮 | 是 | 120 | 300 | 450 | D |
| 被收录进 awesome-list / 他人 README | 是 | 60 | 160 | 250 | D |
| **复利小计（稳态）** | | **360** | **1,500** | **2,500** | |
| Hacker News / 垂直社群脉冲 | **否** | — | — | — | B |

脉冲事件按第 4、9、18、30 月各一次叠加在爬坡曲线上（第 4、18 月按 HN 头版 15,000 UV，第 9、30 月按社群 3,000 UV），见 `model/funnel.py` 的 `pulses` 参数。

### 3.2 机制逐条说明

**① 免费 GitHub Action 本体 —— 产品即渠道**

扫描器以免费 GitHub Action 形式发布。**它的分发机制内建于产品形态本身**：每个安装它的仓库都会在 `.github/workflows/*.yml` 里留下一行公开可见的引用，这一行会被 GitHub 代码搜索索引，也会被该仓库的每一个贡献者读到。安装量即曝光量，且随时间只增不减。

这条渠道回答了"免费版怎么变成分发"的问题，也回答了硬过滤器第 8 条留下的疑问：**免费的一次性扫描是获客层，收费的是 CLI 结构上做不到的持续托管态**（跨时间比对配置漂移、告警、历史基线）。

*诚实标注：*"安装数 → 官网访问"的转化率**无任何公开数据**（`assumptions.MARKETPLACE_INSTALL_TO_PAID` 为 D 级空缺）。表中数字按第 12 月 150 个安装、每安装每月带来约 1.2 次访问推算，是本人假设。

**② 程序化 SEO 知识库 —— 唯一能用 A 级数据自下而上估算的渠道**

内容形态：每个 (agent action × 危险模式) 组合一页。15 个主流 agent action × 12 种危险模式 = **180 页**。每页写清一个具体的错误配置示例、为什么危险、以及可直接复制的修复补丁。

**这不是灌水**：每一页对应一个真实的、可复现的配置错误，搜索这些具体配置名的人正是处于危险三角中的人。

计算（`model/acquisition.py:seo_estimate`）：

```
180 页 × 6.11%（Ahrefs 对英文非空内容的进前十概率）= 11.0 页进前十
11.0 页 × 40 UV/月 = 440 UV/月
```

*诚实标注：* 6.11% 是 A 级（100 万 URL 样本），但 **"一个排进前十的超长尾技术页面每月带来 40 个访客"是 D 级假设，无公开数据支撑**。敏感性网格显示，在 60–300 页 × 15–80 UV/页的合理范围内，结果从 **55 到 1,467 UV/月，跨度 27 倍**。**这条渠道的估算极不可靠，读者应据此打折。**

**③ 负责任披露飞轮 —— 唯一同时满足"向善"与"获客"的动作**

持续在公开仓库中发现真实的 agent CI 配置漏洞，**私下**告知维护者并附上可直接采用的修复补丁。每次披露产生三样东西：一个被修好的仓库、一个知道你是谁的维护者、可能的公开致谢或 advisory 署名。

这条渠道的正当性来自第〇条与第一条：**先创造价值，再谈分享价值。** 发现的问题必须免费完整告知，不得作为付费筹码（见 `docs/WTP_VALIDATION.md` §3 的正向义务）。

间接支持：IndieLaunches 对 326 个 HN 项目的渠道统计中，口碑是被提及最多的主渠道（40 次为主渠道，高于 SEO 的 27 次）。

*诚实标注：* 按每月 10 次披露、30% 回复率、每个回复者平均带来 4 次访问推算，为 D 级假设。

**④ 被收录进清单** —— 安全工具进入 awesome-actions、awesome-ci-security 等清单后获得长期被动引用。取值刻意保守，D 级。

**⑤ HN / 社群脉冲（不计入稳态）** —— 发布原创安全研究，例如"我扫了 5,000 个公开仓库，发现 N 个处于危险三角"。此类内容在本领域传播力最强 —— 微软威胁情报、CSA、Aikido、Noma 四篇来源本身都是靠这个方式传播的。**但按定义只作为一次性事件叠加。**

## 5. 缺口分析：诚实的结论

把计划流量与需求并列：

| | 第 36 月计划稳态流量 | $1,000 MRR 所需 | 覆盖率 | 判定 |
|---|---:|---:|---:|:---:|
| **不要信用卡** | 2,500 UV/月 | 2,729 UV/月 | **92%** | **不足** |
| **要信用卡** | 2,500 UV/月 | 995 UV/月 | **251%** | 足够 |

按计划流量推算的第 36 月 MRR：**不要卡 $916 / 要卡 $2,514**。

**三条必须写进 BP 正文的结论：**

1. **即便所有四条复利渠道都按计划兑现，三年后在不要信用卡的口径下仍达不到 $1,000 MRR。** 这不是保守估计的产物 —— 这是按我自己写的乐观渠道假设算出来的。

2. **"是否要求信用卡"是本项目影响最大的单一决策**，其影响超过任何获客技巧。它把 92% 的覆盖率变成 251%。**建议：从第一天起就要求信用卡开始试用。**
   *但必须同时承认一个反向风险：* ChartMogul 样本中的典型受访者已有 $1M–$10M ARR 与市场团队，**一个无名新产品要求陌生人先绑卡，其转化率很可能不可迁移。** 这正是模型中 `SOLO_NO_TOUCH_DISCOUNT`（0.337）想要吸收的偏差，但该系数本身是 D 级类比推算，无法验证。

3. **四条复利渠道中有三条是 D 级假设。** 唯一有 A 级支撑的是 SEO 的排名概率（6.11%），而它的单页流量假设又是 D 级，敏感性跨度 27 倍。**这一章是本 BP 中论证最详细、但证据最薄弱的一章。** 详细不等于可靠 —— 我把它写长，是因为它最重要，不是因为我最有把握。

## 6. 与 Gate 0-B 的关系

本章全部内容都是**待检验的假设**，不是已验证的结论。`docs/GATE0.md` 的 Gate 0-B（B3 测试：发布免费最小工具，14 天内获得 ≥300 真实独立访客与 ≥30 次实际使用）是对本章第 3.1 节渠道①与③的最小可行检验。

**执行顺序是硬性的：Gate 0-B 未过，本章的一切都不成立，不得据此投入开发工时。**
