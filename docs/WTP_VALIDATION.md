# Gate 1 · 付费意愿证伪方案（头号候选 C12）

> **验证对象：** AI agent 在 CI/CD 中的配置安全审计
> **要证伪的命题：** "存在一群人，愿意为『持续监控我的 CI 里 agent 配置是否处于危险三角』每月付费 $19–49。"
> **约束：零代码、两周内完成、总现金支出 ≤ $12（仅一个域名，可选）。**
> **基准日：2026-07-27**

---

## 0. 为什么这一关必须先于开发

`model/opportunity_scoring.py` 的输出说明了两件事：

1. **C12 在 10,000 次随机权重抽样中夺冠 99.71%，排名对权重极其稳健。**
2. **但它的领先对分数脆弱。** 把 C12 的付费意愿分从 3 归零后，它仅以 **6.43 : 6.17** 领先 C13；把它所有"无外部来源、仅本 BP 自评"的维度各降 3 分后，领先幅度只剩 **0.08**。

换句话说：**C12 之所以排第一，靠的是我最容易评估的维度（可交付性 9 分、边际成本 10 分、痛点证据 9 分），而唯一决定生死的维度——有没有人肯掏钱——是它的最低分（3 分），且这 3 分的唯一依据是 StepSecurity 的间接类比。**

这是一个典型的**评估偏差**：容易测的维度被充分测量，难测的维度被回避。BP 若就此进入财务建模，等于把整栋楼盖在唯一没做地质勘探的那块地上。

**因此本关的判定规则是硬性的：Gate 1 未通过，不写第一行产品代码。**

---

## 1. 证据阶梯：三种"愿意付费"的信号不是一回事

必须先把"付费意愿"这个词拆开。以下三级证据的强度相差一个数量级，BP 中不得混用：

| 级别 | 信号 | 高估倍数 | 说明 |
|---|---|---|---|
| **L1 · 声明性** | "这看起来有用"、点赞、star | **10–50 倍** | 几乎无信息量。人们对免费的赞美不花钱。 |
| **L2 · 承诺性** | 留下邮箱进候补名单（**且已看到明确价格**） | **3–10 倍** | 有一点信息量，前提是**价格必须在留邮箱之前可见**。 |
| **L3 · 交易性** | **真实刷卡付款**（哪怕承诺全额退款） | **1 倍（基准）** | 唯一可信的信号。 |

**纪律：BP 的财务模型只允许引用 L3 证据。L1/L2 只能用于决定"要不要继续往下测"，不得进入 `assumptions.py`。**

---

## 2. 四步测试（总工时 26 小时 ≈ 1.3 周的可投入时间）

### W1 · 受众规模测量（零代码，4 小时）

**要回答：** 处于"危险三角"的公开仓库有多少个？这决定了 TAM 的量级下限。

**方法（全部通过浏览器与公开 API，不写代码）：**

1. GitHub 代码搜索（Web 界面），逐条记录命中仓库数：
   - `path:.github/workflows anthropics/claude-code-action`
   - `path:.github/workflows google-github-actions/run-gemini-cli`
   - `path:.github/workflows openai/codex-action`
   - 上述各项分别叠加 `pull_request_target`（不受信输入的经典入口）
   - 上述各项分别叠加 `permissions: write-all` 或 `contents: write`
2. 记录每个查询的命中数，做交叉估算：**危险三角 ≈ (用 agent action) ∩ (被不受信事件触发) ∩ (持有写权限)**
3. 抽取 30 个命中仓库，人工看其 star 数与所属组织类型（个人 / 创业公司 / 大厂 / 开源基金会），判断"有没有付费能力"

**通过标准：**
- 危险三角命中仓库 **≥ 300 个**，且其中**至少 60 个属于有商业实体的组织**（非纯个人玩具项目）
- 若 < 300：市场规模不足以支撑 $1,000 MRR，**直接淘汰 C12**

> **诚实说明：** 公开仓库只是冰山一角，私有仓库无法测量。因此本步测的是**下限**，用于淘汰而非用于估算 TAM 上限。BP 中不得把这个数字当作市场规模。

---

### W2 · 负责任披露 + 直接问询（零代码，12 小时）—— 本方案的核心

**这一步同时做三件事：真实地帮到人、验证问题真实性、直接测量付费意愿。它是整个方案里唯一能同时满足"向善"与"证伪"两个要求的动作。**

**方法：**

1. 从 W1 的命中集中选 **30 个**仓库，**人工**逐个审阅其 workflow 文件（每个约 15 分钟）
2. 对每个仓库写一份**具体的、可操作的**发现说明（不是模板群发）：
   - 哪个 workflow 文件、第几行
   - 不受信输入从哪里进入 agent 提示
   - agent 持有什么权限、可能外发到哪里
   - 一段可直接采用的修复补丁
3. 通过 **GitHub Security Advisory 私有报告**（若仓库启用）或**维护者邮箱**私下发送，**绝不公开披露**
4. 邮件末尾附**一句**问询，不推销：

   > "我在手工做这类审查。如果有一个服务能在每次 workflow 变更时自动跑这套检查并在发现危险组合时告警，你会为它付费吗？如果会，每月大概多少你觉得合理？如果不会，为什么？（无论回答什么都不影响我继续免费给你发现问题）"

**通过标准（三项全过）：**

| 指标 | 通过线 | 含义 |
|---|---|---|
| 回复率 | **≥ 30%**（30 封中 ≥ 9 封） | 低于此说明问题不被感知 |
| 承认问题真实 | 回复中 **≥ 70%** 确认这是个真问题 | 低于此说明是我在自说自话 |
| **明确表示会付费且给出价格** | **≥ 5 人**，且**中位报价 ≥ $19/月** | **这是本关最关键的一个数** |

**未通过时的处置：**
- 回复率 < 30% → 渠道或表述有问题，**换一种触达方式重试一次**（GitHub Issue 的礼貌提问 / 相关 Discord）
- 承认率 < 70% → **问题不成立，淘汰 C12**，回到机会集取 C13
- 付费人数 < 5 或中位报价 < $19 → **降级为免费工具 + 另寻变现点**，或淘汰

---

### W3 · 价格锚定候补名单（零代码，4 小时）

**要回答：** 在**没有人工对话**的条件下（这才是本项目的真实场景），陌生人看到定价后还愿不愿意留下邮箱。

**为什么必须单独测：** W2 是我一对一手工发信换来的转化，**而本项目的硬约束是零人工**。W2 的转化率**不能外推**到自动化渠道。这两者的差距本身就是重要信息。

**方法（无代码建站工具即可，如 Carrd / Framer 免费档 + Tally 表单）：**

1. 一页落地页，包含：真实的问题描述（引用微软、CSA、Aikido、Noma 四个来源）、W2 中获授权公开的**脱敏**发现示例、**明确的价格表（$19 / $49 两档）**
2. **价格必须在留邮箱按钮之前可见。** 先要邮箱再谈价格的漏斗测不出付费意愿，只能测好奇心。
3. 按钮文案必须诚实：**「加入候补名单（产品尚未发布）」**，不得写「开始免费试用」或「立即购买」
4. 把 W2 中的发现（脱敏后、获维护者同意）整理成一篇技术文章，发到 Hacker News 与 2 个垂直社群

**通过标准：**
- **访客 → 候补名单转化 ≥ 3%**（对照：`BENCHMARKS.md` 中访客→注册基准为 4.5%，本页因明示"尚未发布"应低于该值，3% 已属合格）
- 候补名单绝对数 **≥ 50 人**

---

### W4 · 预付款测试（零代码，6 小时）—— 唯一的 L3 证据

**要回答：** 有没有人真的会刷卡。**这是唯一能进入 `assumptions.py` 的证据。**

**方法：**

1. 用 Paddle / Gumroad 的**托管结账页**（零代码，复制粘贴一个链接即可），创建一个"创始用户"档位：**$99 一次性，覆盖首年**
2. 页面必须**极其明确**地写清（这几条是道德底线，不可省略）：
   - **产品尚未开发完成，预计 XX 周后交付**
   - **任何时间、无理由、全额退款，无需说明原因**
   - 交付失败则**主动**全额退款，不需要客户申请
   - 首年后是否续费完全自愿
3. 只向 W2 中明确表示"会付费"的人和 W3 候补名单发送**一次**，不催促、不制造稀缺感、不设倒计时

**通过标准：**
- **≥ 3 人真实完成付款**（$297）

**这个数字为什么定在 3：** 按 `BENCHMARKS.md` 的漏斗，50 人候补名单在 3% 注册→付费下期望值约 1.5 人。要求 3 人是要求**显著优于基准**。若连 3 个"我已经手工帮他找出真实漏洞的人"都不肯预付 $99，那么面对陌生流量的转化只会更差。

**若付款人数为 0：** 结论明确 —— **付费意愿不成立，C12 淘汰。** 此时应把已做的手工审查工具化为免费开源项目回馈社区（这在 W2 中已经承诺过，必须履行），然后回到机会集取 C13。

## 3. 道德底线（不可协商）

对应工作原则第〇条（向善）、第三条（诚实守信）、第五条（合法合规）：

| 禁止 | 理由 |
|---|---|
| **假的结账按钮 / 假的"立即购买"** | 欺骗。即便业界常用，本项目不采用。 |
| **假的稀缺与倒计时** | 操纵。 |
| **公开披露未修复的漏洞以制造恐慌** | 违反负责任披露准则，且可能损害真实用户。 |
| **群发模板邮件** | 无价值，且构成骚扰。**每一封必须包含针对该仓库的具体发现。** |
| **把 W1 的公开仓库数当作市场规模写进 BP** | 那是下限不是规模，属于夸大。 |
| **收了预付款却不退** | 底线。W4 的退款承诺是无条件的、主动的。 |

**一条正向义务：** 无论 W2 的商业结论如何，**已发现的安全问题必须免费、完整地告知维护者，不得以此作为付费的筹码**。这不是营销策略，这是发现漏洞后应尽的责任。

## 4. 判定汇总与后续动作

| 关卡 | 通过标准 | 未通过时的动作 |
|---|---|---|
| W1 受众规模 | 危险三角仓库 ≥ 300，其中商业组织 ≥ 60 | **淘汰 C12** |
| W2 承认率 | ≥ 70% 的回复确认问题真实 | **淘汰 C12** |
| W2 付费表态 | ≥ 5 人明确会付费，中位报价 ≥ $19/月 | 降级为免费工具或淘汰 |
| W3 自动化转化 | 访客→候补 ≥ 3%，候补 ≥ 50 人 | 保留赛道，但**获客假设必须重写**（说明零人工触达无效） |
| **W4 真实预付** | **≥ 3 人付款** | **淘汰 C12，转 C13** |

**四关全过 → 进入 Gate 2（构建 MVP），且此时 `assumptions.py` 中的付费转化率可以用 W4 的实测值替换基准值。**

## 5. 这个方案本身的弱点（自我批评）

必须承认三点，否则就是在自欺：

1. **W2 的高接触度无法外推。** 我手工写 30 封带具体发现的邮件，转化率一定高于任何自动化渠道。**这正是 W3 存在的理由，但 W3 的样本量（50 人量级）在统计上仍然很弱。** 3% 的转化率若来自 60 个访客中的 2 人，其置信区间宽到几乎无信息量。BP 中引用 W3 结果时必须同时报告样本量与区间。

2. **W4 的 3 人门槛是拍脑袋的。** 它的依据是"显著优于基准"这一定性要求，不是统计功效计算。以 n=3 判定一个商业模式，本身就是在小样本上做大决策。**我选择它不是因为它科学，而是因为在两周、零成本的约束下没有更好的选择。** BP 中必须如实标注这一局限。

3. **本方案测的是"现在的付费意愿"，不是"产品做出来之后的付费意愿"。** 有些产品必须先存在才能被理解。预付款测试对这类产品会系统性低估。**我接受这个偏差，因为在单人 20 小时/周的约束下，"先做出来再看有没有人要"的代价（12 周 ≈ 240 小时）远高于误杀一个好想法的代价。** 这是一个明确的、有意识的取舍，不是疏忽。
